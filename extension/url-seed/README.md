# 造梦西游3 种子恢复（URL 随机数）· 浏览器扩展

在游戏页面上**自动**从网络请求里挑出随机数，凑够两个就恢复种子，并在页面右下角飘一个面板显示结果。

为什么必须是扩展、而不是网页版的一小段脚本：

* 造梦西游3 是 Flash，随机数是 Flash 自己发的请求（`URLLoader`），
  **页面里的 JS 钩 `XMLHttpRequest` / `fetch` 是看不到的**；
* 只有扩展的 `webRequest`（后台 Service Worker）能看到全部请求的 URL。

恢复算法本身**一个字都没重写**：直接把网页版的 `web/src/scenarios/seed_resolve.ts` 与
`web/src/wasm/cracker.wasm` 拿来用，所以结果与网页版逐位一致。

---

## 一、安装（开发者模式加载）

1. 在 `web/` 下构建：

   ```sh
   npm run build:ext
   ```

   产物在 `web/extension/url-seed/dist/`（已在 `.gitignore` 里，不入库）。
   调试时用 `npm run build:ext:debug`（不压缩，出问题好看行号）。
2. 打开 `chrome://extensions`（Edge 是 `edge://extensions`）→ 右上角打开 **开发者模式**；
3. 点 **加载已解压的扩展程序** → 选 `web/extension/url-seed/dist` 这个文件夹；
4. 需要 **Chrome / Edge 116 或更高**（`minimum_chrome_version`）。

> ⚠️ 一定要选 **`dist`**，不要选它的上级 `url-seed/`。
> 选错时 Chrome 会报「**无法加载背景脚本 background.js / 无法加载清单**」——
> 因为上级目录里没有 `background.js`（它只在 `dist/` 里）。

> 🧓 **旧内核（Chromium 70 级，或 Chrome ≤ 126）**：MV3 根本装不上（详见下表那段说明），
> 请改用 **MV2 档** —— 同一份源码、另一份清单，见
> [`../url-seed-mv2/README.md`](../url-seed-mv2/README.md)。

改完代码不用卸载，回到扩展页点一次 ⟳ 刷新即可（游戏页面要一起刷新）。

## 二、用起来

1. 打开游戏页面（比如 `https://sx.4399.com/...`）；
2. 点地址栏右边的扩展图标，在弹出的**小窗口**里点
   **「开启 xxx 的监听」** —— 这一步会申请该网站的权限并把站点记下来。
   权限申请**必须**在点图标这一下完成（`activeTab` 只在用户手势里有效），
   所以只能在这里做，设置页里做不到；
3. 游戏里**保存游戏两次**（或触发任意两次带随机数的请求）；
4. 页面右下角出现面板，抓到第二个不同的随机数后**自动**恢复，显示 `种子: 2097477657`。

面板上的东西：

| 控件 | 作用 |
| --- | --- |
| 标题栏的 `−` | 收起 / 展开（收起后只剩一条细条，不挡操作） |
| 自动恢复 | 关掉后就只在点「恢复」时才计算 |
| 恢复 / 清空 | 手动用**当前**最近两个值算一次 / 丢掉已抓到的值重新开始 |
| 结果区 | `种子: N`，或 `种子: N（已后移 M 步）`，或 `没有命中…（无候选）`、`…（N 个候选，无法唯一确定）` |
| 最近请求（调试） | 每一条抓到的 URL 与取到的数字，判断「这个值到底对不对」就看它 |

图标的弹窗里也能看到当前页面的状态（抓到几个、算出什么），不用展开面板。

### 两个值是**连续两次**抽样

恢复成立的前提是：这两个随机数是游戏随机序列里**紧挨着的两次**。
所以两次保存之间不要夹别的会抽随机数的操作，否则这次算不出来 ——
面板会直接说 `没找到`，换一对值再试即可。

两个值还必须**不一样**：同一个值不会被当成一对（否则会白白算一次）。

### 恢复出的种子是「读出匹配值**之前**」的那个

拿到的是**匹配值被抽出来之前**的那个种子 —— 匹配值本身是从它往后走**一步**得到的。
用 golden 那组数可以自己验：

```
恢复出           种子: 2097477657
FastNext 一步    → 1988262924      ← 匹配值 967974830 正是从 2097477657 这一步抽出来的
```

所以如果游戏在那之后又抽了 N 次随机数，你要的种子就比它**靠后**更多步 ——
这时用规则的「**后移次数**」把 N 补上，结果区会写成
`种子: 2097477657（已后移 3 次 FastNext）`。

* 只在**唯一解**时才后移；`没找到` / 多候选时原样端出，不做无谓加工。
* 两个读数来自**不同规则**、后移次数又不一样时，以**匹配值那条**（更晚那个读数）为准 ——
  要补的本来就是「产出匹配值的那个动作之后的推进」。
* 「后移次数」按**当前规则表实时读**：改完设置立刻生效，不用重抓值；
  但把那条规则删了就会回落到 0。
* 步进是**朴素循环**（不用快速幂/jump）：N 就是个位数，没必要为它引一套矩阵算法。
* 上限 1000（防手输巨值把页面卡住）。正常用法是个位数。

## 三、默认规则（五条内置）

URL 长什么样各不相同，同一个 `ran=` 参数在不同接口里含义也不同，所以「哪条 URL 算数、怎么换算」是**规则**，不是硬编码：

| 规则 | 匹配 | 处理 | 换算 | 后移次数 |
| --- | --- | --- | --- | --- |
| 忽略 `over/entries` | `over/entries` | **跳过** | —— | —— |
| 保存游戏 `get_token` | `ac=get_token` | 取数 | `int(n / 100000 * 0x80000000)` | `0` |
| `flash_ctrl_version.xml` | 文件名 | 取数 | 同上（也是显示值） | `0` |
| `flash_ad_version.xml` | 文件名 | 取数 | `int(n * 0x80000000)`（原始浮点） | `0` |
| 授时 `get_time` | `ac=get_time` | 取数 | `int(n * 0x80000000)`（原始浮点，数字直接当参数） | `2` |

出厂值里**只有 `get_time` 那条是 `2`**，其余四条都是 `0`（= 不后移，和以前的版本行为完全一样）。
「授时」是给**斗部群星**那类流程用的：`get_time` 把随机数端出来之后，游戏还会再往后走
2 步才轮到你要的那个数，所以它出厂就带 2。
只有你确知「之后又抽了 N 次」时才去改它 —— 通常是为某一条接口单独调。

为什么 `over/entries` 必须**挡掉**：那里的 `ran=86213.62410485744` 只是 4399
自己的接口参数，`×0x80000000` 之后超出 31 位随机数的范围，喂进去只会报
「超出 31 位随机数范围」。默认规则的顺序就是**优先级**（从上往下第一条命中的生效）。

`ran=` 的提取正则默认是 `(?:[?&]|^)ran=([^&#\s]+)`：`?ran=`、`&ran=` 都能取，
且**必须有一个 `(…)` 捕获组**（没有捕获组时会直接报错，不会静默取错）。

**没匹配上任何规则 ⇒ 不猜**。宁可什么都不做，也不要拿一个来路不明的数字去恢复。

## 四、公式怎么写

规则里的「换算公式」是一小段算术表达式，输入只有一个变量 `n`
（从 URL 里提取到的那串数字），输出必须是 **0 ~ 2147483647 的整数**。

* 运算符：`+ - * / %` 与括号 `( )`，同级左结合（`8 / 4 * 2` 是 `(8/4)*2`）；
* 数字：十进制，或十六进制 `0x80000000`；
* 函数：`int` / `trunc` / `floor` / `ceil` / `round` / `abs`（单参数）；
* 变量：只有 `n` 一个。

两条内置公式：

```
int(n / 100000 * 0x80000000)   ← 「保存游戏」那串显示值，被游戏乘了 100000，先除回来
int(n * 0x80000000)            ← 原始浮点（flash_ad_version.xml 那种）
```

设置页的「公式怎么写」一节就是这几行，跟着代码里的 `FORMULA_HELP` 走。

> MV3 的 CSP 禁止 `eval` / `new Function`，所以这个公式是**手写的词法器 + 递归下降解析器**
> （`src/formula.ts`），不是 `eval`。构建脚本里还有一道 `assertNoEval()` 兜着。

## 五、「恢复默认」到底恢复什么

设置页有一个 **恢复默认规则** 按钮，语义写死为：

* **内置规则**：被删掉就补回来、被改乱了就还原成出厂样子，且**位置不动**；
  少了的内置规则按内置顺序插回列表前面；
  「被改乱」也包括**后移次数** —— 内置的那五条会被恢复成**出厂值**
  （`get_time` 是 `2`，其余四条是 `0`）；
* **你自己建的规则**：一个字都不动，不会被删、也不会被复活。

也就是说，删掉「忽略 over/entries」这种操作是可以后悔的；而你自己加的规则是安全的。
详见 `src/rules.ts` 的 `restoreDefaults`。

`新建规则` 给的是「保存游戏」形态的骨架（提取 `ran=` + `÷100000` 公式），改一改就能用；
也可以直接点某条 URL 旁边的「用来新建规则」把样例填进去。

## 六、只监听你授权的网站

* 扩展安装时**不申请任何网站权限**，`optional_host_permissions` 里只有一个 `*://*/*`；
* 只有你在弹窗里点了「开启监听」，才会为该域名申请权限，并把 pattern 记进
  `chrome.storage.local`；
* 权限被撤销（比如在扩展页里手动收回）时，内容脚本会被注销，弹窗会提示
  **「重新授权」**；
* 权限白名单是**尽力而为**的：`webRequest` 只对已授权的域名触发，但 `webRequest`
  拿不到未被授权站点的 URL —— 这正好就是我们要的边界。

所有数据（规则、站点、已抓到的值）都只存在**本机** `chrome.storage.local`，
不发任何网络请求（wasm 是 Base64 内联在 `content.js` 里的，不下载）。

> 清单与两个 HTML 放在 `src/` 里、而不是扩展根目录，是**故意的**：
> 它们只是源，`dist/` 才是能加载的成品。如果根目录也放一份 `manifest.json`，
> 在 `chrome://extensions` 里误选 `url-seed/` 时 Chrome 读得到清单、却找不到清单点名的
> `background.js`，于是报「**无法加载背景脚本 background.js**」—— 这句话指向的位置是错的，
> 很难查。现在选错了只会得到「清单文件缺失或无法读取」，一眼就知道是选错目录。

构建：`web/tools/build_extension.mjs` —— 用 Vite（rolldown）把四个入口各打成 IIFE，
把 wasm 以 `self.__RNG_SINGLEFILE__` 内联进 `content.js`，并在产物上跑三道检查：

1. `assertParses` —— 产物必须能被 JS 引擎解析；
2. `assertNoEval` —— 产物里不许出现 `eval(` / `new Function`（MV3 CSP）；
3. `assertManifestComplete` —— 清单里引用的文件必须都真的产出了。

测试：`web/tests/ext_*.test.ts`（`formula` / `rules` / `select` / `sites` / `resolve`），
随 `npm run test` 一起跑，**不需要浏览器**：`chrome` 相关的部分都有兜底。

```sh
cd web
npm run typecheck     # 含扩展源码
npm run test
npm run build:ext
```

## 八、面板不会永远卡在「恢复中…」：wasm 加载这一层的闸门

面板显示「恢复中…（值 → 值）」并把「恢复」按钮按灰，等价于 `content.ts` 里的 `busy === true`；
而 `busy` **只**会在 `resolver.resolve(...)` 返回或抛出之后被 `finally` 放回去。
⇒ 「永远停在恢复中」这件事只有一个成因：**那个 promise 既不肯成功也不肯失败**。

`Resolver.ensure()` 里那份加载 promise 是**所有**恢复共用的（并发时只加载一次），
它悬住就是全面板的事故；而 emscripten 那边只有「成」和「败」两条路，**没有**「等多久算失败」。
所以闸门装在 `resolve.ts`：

- 单次尝试最多 `LOAD_TIMEOUT_MS = 10` 秒；
- 总计 `LOAD_ATTEMPTS = 2` 次 —— 刷新页面那一下最典型的失败是「请求发出去了、然后没了下文」，
  隔开一次重新发起往往就成了；
- 全都不成才抛 `ResolveError`，`runResolve` 的 `catch` 会把它显示成
  `恢复失败：加载 cracker.wasm 失败（已尝试 2 次）：…` 并把按钮放回去（而不是无声无息地卡住）；
- **失败不缓存**：`ensure()` 只在成功时记下运行时；失败会清掉 `pending`，
  下一次点「恢复」重新加载。

预热（面板一展开就调的 `resolver.warmup()`）失败同样会写进状态栏，不再只躺在调试日志里。

回归锁在 `web/tests/ext_resolve.test.ts` 的「wasm 加载悬住时的兜底」三条：
注入一个**永不 settle** 的 `create`（`ResolverOptions.create`，只为测试存在），
用假定时器把 10 秒 × 2 快进过去，断言它抛 `ResolveError` 而不是永远 pending、
重试成功时照样能恢复、失败之后下一次会重新加载。
